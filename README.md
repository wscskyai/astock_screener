# A 股选股系统（astock_screener）

本地化 A 股选股工具：把日线、财务、股东户数、估值全部落到本地 SQLite，
盘后增量同步，查询与形态计算全在本地跑；自带 Web 界面（指数看板 / 选股筛选 / 收藏跟踪）。

- **数据**：5,578 只股票、713 万行前复权日线、估值分位、股东户数与财报（带公告日，可做 point-in-time）
- **形态**：做小做底、低位放量、旗形整理 / 突破、箱体、W 底、底部启动
- **界面**：指数分时与日/周/月 K、30 个可筛指标、收藏分组与跟进笔记、个股 K 线弹窗
- **部署**：单机 `python web/app.py`，或 Docker / NAS（见下方章节）

## Docker / NAS 部署

镜像里只装 Python 运行时 + pandas/numpy，数据库（1.1 GB）通过 volume 挂载，不进镜像。

```
astock_screener/
├── astock/               ← 核心包（数据层 / 指标 / 形态）
├── tools/                ← 命令行脚本
├── web/                  ← 站点
├── Dockerfile
├── docker-compose.yml
├── requirements.txt
└── data/                 ← 挂载进容器：./data:/app/data
    └── astock.db
```

### 在 PC / 服务器上跑

```bash
docker compose up -d --build      # 首次会装依赖，约 3~5 分钟
docker compose logs -f            # 看启动日志
```

打开 `http://<IP>:5001`。健康检查走 `/api/me`，`docker ps` 里显示 `(healthy)` 就绪。

### 放到群晖（Container Manager）

1. **准备目录**：在共享文件夹（如 `docker/astock`）里放入代码（或只放 `Dockerfile`+`docker-compose.yml`+项目文件），
   再建 `data/` 子目录。
2. **放入数据库**（推荐，省掉首次全量下载）：把 PC 上的 `data/astock.db`（约 1.16 GB）复制到
   `docker/astock/data/astock.db`。只有这一个文件即可，`-wal`/`-shm` 不用带。
3. **启动**：
   - Container Manager → 项目 → 新增 → 选择该目录的 `docker-compose.yml` → 构建并启动；
   - 或 SSH 进 NAS：`cd /volume1/docker/astock && sudo docker compose up -d --build`
4. **访问**：`http://<NAS_IP>:5001`。

> 如果 NAS 上不方便 `build`（很多型号没有编译器、拉 pypi 慢），可以在 PC 上构建后导出，
> 再把 tar 传到 NAS 加载。`docker-compose.yml` 里把 `build: .` 注释掉即可直接 `up -d`。

```bash
# PC 上导出镜像
docker save astock-screener:latest -o astock-screener.tar

# 传到 NAS 后加载
sudo docker load -i astock-screener.tar
```

### 首次没有数据库时

容器会在挂载目录里自动建空库（表结构、12 个默认筛选方案），然后可以：

```bash
# 全量拉一次日线/财务/股东户数（20~40 分钟，取决于网络）
docker compose run --rm astock python tools/build.py init

# 之后日常增量
docker compose run --rm astock python tools/build.py update
```

也可以直接在网页「本地库」面板里点同步（需要登录），或把 `sync_time` 设成交易日晚间（如 18:30）让容器自动同步。

### ⚠️ 数据库不要放在同步盘里（disk I/O error 的根源）

如果启动后日志出现：

```
数据库读取失败：disk I/O error
!! GET /api/me -> OperationalError: disk I/O error
```

八成是 **`data/astock.db` 放在了同步盘 / 网盘目录**（OneDrive、坚果云、fnOS 同步客户端等），
同步客户端会一直占用 SQLite 的 `-shm` 共享内存文件；这个文件是**平台相关**的，
Linux 容器打开 Windows 生成的 `-shm` 就会直接报 `disk I/O error`（`dd` 读文件却正常）。

处理办法：**把数据库挪到本地普通目录**（不要同步），用环境变量指过去：

```bash
# docker-compose 同目录建 .env（已被 .gitignore 忽略）
ASTOCK_DATA_DIR=D:/astock_data
```

```bash
# 主机直接跑时
set ASTOCK_DB=D:\astock_data\astock.db
python web/app.py --port 5001
```

另外两条相关命令：

```bash
python tools/build.py checkpoint --drop-shm   # 合并 WAL、删掉 -shm（切换主机/容器前跑一次）
```

代码里也做了自愈：`db.connect()` 遇到打不开且存在 `-shm` 时，会自动把它改名挪开再重试，
并从 `-wal` 重建（数据不丢）。容器默认还开了 `ASTOCK_SQLITE_SAFE=1`（不用 WAL、不用 mmap）。

> 同一时间只让**一个**进程打开数据库：主机上的服务和容器不要同时开着同一个库。
> 主机端口被占用时 `web/app.py` 会自动顺延到 5002，容易变成「两个实例都在跑」，
> 建议用 `docker compose down` 或杀掉本机 python 后再启动容器。

### 注意事项

| 事项 | 说明 |
|---|---|
| **存储位置** | `data/` 必须是 NAS 本地存储（btrfs/ext4）。**不要挂 SMB/NFS 网络盘**——SQLite 的 WAL 在网络文件系统上会损坏数据 |
| **权限** | 容器内以 root 运行；如果 NAS 上 data 目录属主特殊，`chown -R 1000:1000 data` 或 `chmod 777 data` 也可（本地自用场景） |
| **端口** | 默认 5001；群晖 5000/5001 常被 DSM 占用，映射成 `5002:5001` 之类即可 |
| **时区** | 已设 `TZ=Asia/Shanghai`，分时/交易时段判断依赖它 |
| **内存** | 实测常驻约 1.4 GB（预热完成后），compose 里给了 3 GB 上限；NAS 建议留 ≥2 GB 可用 |
| **架构** | `python:3.12-slim` + pandas/numpy 在 x86_64 和 arm64 都有 wheel，群晖/威联通两种机型都能跑 |
| **数据目录** | 默认 `./data`，可用 `.env` 的 `ASTOCK_DATA_DIR` 指到别的盘；**不要放同步盘/网盘**（会导致 disk I/O error，见上） |
| **公网访问** | 建议走 NAS 自带的反向代理 + HTTPS，别直接把 5001 暴露到公网；本项目只有密码登录（PBKDF2 加盐），没有二次验证 |

## 启动与性能

启动慢曾经是最大的体验问题（日线预热 262 秒、K 线接口 2 分钟打不开）。原因和处理：

| 问题 | 原因 | 处理 |
|---|---|---|
| K 线接口超时 | 弹窗画 W 底/做小做底标记时调 `patterns._bars()`，把**全市场 713 万行**读进内存 | 新增 `_bars_one()`，只读这一只票（**7ms**） |
| 日线预热 262 秒 | 全量加载 + 冷盘 + 与分位预热抢 CPU | 只加载**最近 520 个交易日**（形态最多用 260 根）→ **8.8 秒**；并加锁避免并发请求各读一遍 |
| 分位预热 42 秒 | 每次启动都重算 | 加 `pct_stale()`：数据日期没变就跳过（平时启动 0 秒） |
| 预热跟首屏抢资源 | 起动即全速跑 | 预热延后 2~3 秒启动，先让首屏接口跑完 |

实测（同时开 1 个实例，冷启动后立刻访问）：

```
/                        0.01s
/api/me                  0.02s
/api/stock_list?limit=20 0.92s
/api/kline/688183        0.03s      ← 修复前 2 分钟+
/api/screen?limit=20     3.06s      ← 冷启动建宽表，之后 ~0.6s
日线预热完成              18.7s（后台）
```

> ⚠️ 不要同时开两个实例（比如 5001 和 5002）：两个进程都会读 1.1 GB 的库做预热，
> 磁盘争抢会让启动慢好几倍。

## 选股页的「我的收藏」列表

筛选结果区有三个标签：**个股列表 / 筛选结果 / 我的收藏**。

「我的收藏」用和个股列表一样的表格展示（不是 /fav 的卡片墙），列包括：
现价、涨跌幅、成交量、换手率、流通市值、总市值、PE、PB、行业，另外多了 **分组** 和 **跟进**（笔记条数）。

- 接口：`GET /api/favorites_list`（需登录），支持 `sort` / `dir`
- 点表头可排序（本地排序，收藏一般就几十只）
- 点某一行 = 选中该股，右侧走势图和弹窗跟个股列表一致
- 在列表里点 ★ 增删收藏后，这个标签会自动失效，下次切过去重新加载
- 不分页（一页显示完），底部显示「共 N 只」

## 单只股票同步 K 线（手动）

不用跑全市场，也能把关注的票补到最新：

- 接口：`POST /api/bars/sync`  body `{"symbol": "600642"}`
- 返回：`{ok, symbol, name, rows, latest, fixed, n_bars, seconds}`
- 行为：先拉最近 40 天做增量；如果发现**复权漂移**（除权除息导致前复权价整体变化，
  重叠日期收盘价差 > 0.3%），自动改成整只重建（`fixed: true`）。
  比较时**跳过当天那根未收盘的 K 线**，否则盘中价格一动就会被误判成除权、每次都全量重建
- 写完会清掉筛选结果缓存、宽表缓存、形态缓存和内存里的 K 线，下一次查询就是新数据
- 不传 `symbol` 返回 400；代码不存在返回 400「没有找到股票」

界面上有两个入口：

| 位置 | 说明 |
|---|---|
| 收藏页每张卡片 | 「同步」按钮（在「移除」旁边），点完刷新这张卡的数据 |
| K 线大图右上角 | 「同步」按钮，点完重新加载该股 K 线 |

实测（2026-11-18 盘中）：

```
收藏页点「同步」比依股份 603215 → 已同步：1152 根，最新 2026-11-18（检测到除权，整只重建）
弹窗点「同步」申能股份 600642 → 已同步：29 根，最新 2026-11-18
```

## 筛选结果分页

`GET /api/screen` 支持服务端分页与排序，表格只取当前页：

| 参数 | 说明 |
|---|---|
| `conds` | 条件 JSON（必填） |
| `limit` | 每页条数；`0` 或不传 = 不分页（返回全部） |
| `offset` | 跳过多少条（`(页码-1) × limit`） |
| `sort` | 排序列：`symbol / drop_pct / profit_yi / mktcap / float_mktcap / pe / pb / dv / roe_annual / yoy / rev_yoy / gross_margin / period` |
| `dir` | `asc` / `desc`（默认 `desc`） |

返回里 `count` 始终是**命中总数**，`rows` 只是当前页，另外附带 `offset` / `limit`。

前端（`app.js`）已经全部改走服务端分页：

- 表头点击排序、每页条数（20/50/100/全部）、翻页按钮都会重新请求接口
- 底部显示「共 N 只 · 第 X~Y 条」和「第几页 / 共几页」
- **导出 CSV 仍导出全量**：单独再请求一次 `limit=0`
- 深链接：`/screen?size=20&page=3&sort=pe&dir=asc` 直接定位到某一页

效果（默认条件 280 只命中）：

| 请求 | 响应大小 | 耗时 |
|---|---|---|
| 不分页（全部 5382 行） | 2061 KB | 52 ms |
| `limit=50` | 19 KB | 15 ms |
| `limit=50&offset=500` | 19 KB | 3 ms |
| `limit=100&sort=pe&dir=asc` | 39 KB | 30 ms |

> 顺手修了结果缓存没有上限的问题：`_CACHE` 之前只判断 120 秒有效期、从不删除过期条目，
> 每套条件的结果（5000 多行 × 一份）都常驻内存，几十次查询就能涨到几个 GB，
> 服务端内存被打满后请求开始超时。现在过期即删 + 最多保留 16 套。

## 指数首页

- **宽屏布局**：顶部一条横向指数带（12 个：上证/深成/创业板/科创50/北证50/科创综指/
  沪深300/中证500/中证1000/上证50/中证全指/恒生指数），每格显示名称 + 当日涨跌幅，
  未选中的格子有淡边框，选中后加深并高亮；点一下切换
- 下面一条当日数据栏：最新 / 最高 / 最低 / 成交额 / 成交量 / 数据时间，右侧有
  **同花顺** 按钮（`stockpage.10jqka.com.cn/1A0001/` 这类页面，按指数映射）
- 图表占满剩余窗口高度（`calc(100vh - 330px)`），一屏看全 主图 + VOL + MACD
- 左侧报价卡：点位、涨跌、涨跌幅、今开 / 昨收（周/月模式显示「上周收 / 上月收」）/
  最高 / 最低 / 成交额 / 成交量
- 右侧图表 **4 个视图**，每个视图都是「主图 + 成交量 VOL + MACD」三段式：

  | 视图 | 主图 | 说明 |
  |---|---|---|
  | 分时 | 价格线 + 面积 | 今日 / 5 日两种档；昨收虚线 + 右侧双刻度（点位 + 涨跌幅） |
  | 日K / 周K / 月K | 蜡烛 + MA5/MA20 | 300 根，日期刻度 `YY-MM-DD` |

- MACD 都是标准 12/26/9（DIF、DEA 双线 + 红绿柱，零轴分界），成交量柱与 K 线同色
- 十字光标：竖线 + 横线 + 提示（时间/日期、价格、涨跌幅；K 线模式显示 开/高/低/收）
- **数据不入库**：分时调东财 `trends2`（20 秒内存缓存），K 线调东财 `kline`（5 分钟缓存）；
  交易时段分时每 30 秒自动刷新
- **分时横轴按「全天交易时段」定位**：A 股 241 个分钟槽位（09:30–11:30 / 13:00–15:00）、
  恒生 331 个（09:30–12:00 / 13:00–16:00）。开盘 10 分钟就只占约 4% 宽度，右侧留白，
  盘中长度随实际时间增长；5 日模式按「5×全天」铺满，当天未走完的部分同样留白
- 分时 MACD 设了最小纵轴范围（价格的 0.1%），避免开盘几分钟把噪声放大成大柱子
- 深链接：`/?idx=HSI` 直接看恒生、`/?days=5` 看 5 日分时、`/?mode=day|week|month` 看 K 线
- 指数批量行情：`GET /api/index/quotes`（一次拿 12 个指数的涨跌幅/高低/成交额，10 秒缓存）
- 恒生指数走东财港股指数通道（`scid=100.HSI`），分时 331 点（09:30~16:00 含午休），
  成交额单位是港元
- 中证全指（000985）同花顺没有对应指数页，按钮改为跳东财 `quote.eastmoney.com/zs000985.html`
- 接口：`GET /api/index/list`、`GET /api/index/minute?code=000001&days=1`、
  `GET /api/index/kline?code=000001&period=day|week|month&n=300`
- 深链接：`/?mode=day`、`/?mode=week`、`/?mode=month` 直接打开对应视图

> 说明：东财对指数返回的第 8 个字段不是「均价」（数值会落在当日高低点之外），
> 所以分时图只画价格线，没有均价线。

### 指数 PE / 估值（调研结论：免费源拿不到）

试过的接口都不给指数估值：

| 来源 | 结果 |
|---|---|
| 东财 `push2his` / `ulist` 的 `f9` | 指数返回 `-` |
| 东财 `stock/get` 的 `f162/f167/f92`（PE/市值） | 全是 0 |
| 中证指数官网 `csindex.com.cn` API | 404 |
| 乐咕乐股 `legulegu.com` 指数估值接口 | 404 |
| 同花顺指数页（我们外链的那个） | 页面里没有「市盈率」字样 |

可行方案（都需要额外投入）：

1. **按板块估算**：用库里个股 PE + 总市值加权，能算「沪市/创业板/科创板」这类近似值，
   但沪深300、中证500、中证1000 需要真实成分股名单，东财的成分接口（`fs=i:secid`）
   只返回指数本身，拿不到成分
2. **自建历史分位**：每天收盘把估算 PE 存一份快照，积累几个月后才有分位意义
3. **付费源**：理杏仁 / Wind / Choice 有指数 PE 与历史分位

在没有可靠数据前，首页不展示指数 PE，避免给出错误估值。

## 数据层说明

多市场选股程序的第一块地基：**把 A 股所有选股要用的数据落到本地**，之后所有查询都读本地库，
接口只负责增量更新。

## 1. 本地还是实时调接口？

**本地。** 理由：

| 维度 | 每次调接口 | 本地库 |
|---|---|---|
| 速度 | 全市场 5500 只 × 3 类数据 ≈ 十几分钟，且每次都要重跑 | 全市场扫描 20~30 秒 |
| 稳定性 | 免费源随时限流（实测东财、腾讯会在持续请求后被临时封） | 接口挂了不影响查询 |
| 可复现 | 数据每天都在变，昨天的结果无法复现 | 同一份库，结果可回放 |
| 回测 | 几乎不可行 | 需要历史时直接查 |

接口只在**建库**和**每日增量**时调用，其余时间完全离线。

## 2. 表结构

单文件 `data/astock.db`（SQLite，无需额外依赖）：

|---|---|---|

## 4. 命令

```bash
python tools/build.py init                  # 全量建库（首次，约 15~20 分钟）
python tools/build.py init --limit 100      # 小样本试跑
python tools/build.py update                # 每日增量：只补最近 40 天日线
python tools/build.py update --fundamentals # 每周增量：含股东户数/财务
python tools/build.py status                # 库状态
python tools/build.py validate              # 数据体检
```

查询示例：

```bash
python -m astock.query holders --min-drop 5              # 股东户数三季连降、累计降幅 ≥5%
python -m astock.query profit --min 10000000             # 近三季单季净利之和 ≥1000 万
python -m astock.query combo --min-drop 8 --min-years 5 --mktcap 50 200 --exclude-st
python -m astock.query bars 600000                       # 看单只票日线
```

三个筛选条件（`holders` / `profit` / `combo` 均支持）：

| 参数 | 说明 | 示例 |
|---|---|---|
| `--min-years N` | 上市满 N 年（按 `list_date`，缺失则剔除） | `--min-years 5` |
| `--mktcap` | 总市值（亿元）：1 个值=下限，2 个值=区间 | `--mktcap 100` / `--mktcap 50 200` |
| `--exclude-st` | 剔除名称含 ST 的股票 | `--exclude-st` |

### 多条件组合（AND）

一条命令写全，条件之间取交集：

```bash
# 近三季股东户数减少 20% + 市值 50~100 亿 + 近三季净利 ≥ 0.1 亿
python -m astock.query combo --min-drop 20 --profit-yi 0.1 --mktcap 50 100 \
                       --exclude-st --min-years 5
```

| 条件 | 参数 | 口径 |
|---|---|---|
| 户数三季连降 | `--min-drop 20` | 最新期比 3 期前**累计降 ≥20%**，三期须连续季末 |
| 市值区间 | `--mktcap 50 100` | 总市值 50~100 亿；单值表示下限 |
| 净利润 | `--profit-yi 0.1` | 近 3 个**单季**归母净利之和 ≥0.1 亿；元为单位用 `--min-profit 10000000` |
| ROE | `--min-roe 10` | 最新报告期 ROE **年化** ≥10%（Q1×4、半年×2、三季×4/3） |
| 净利同比 | `--min-yoy 0` | 最新报告期净利润同比 ≥0% |
| 市盈率 | `--max-pe 15` | PE(TTM) ≤15；亏损股（PE≤0）自动排除 |
| 股息率 | `--min-dv 3` | 近 12 个月股息率 ≥3% |
| 非 ST | `--exclude-st` | 名称不含 ST |
| 上市年数 | `--min-years 5` | 上市满 5 年 |
| 次新 | `--min-bars 250` | 默认启用：K 线不足 250 根剔除 |

### 估值数据（PE / PB / 股息率）

估值是**日频**的：PE = 收盘价 / 每股收益，收盘价每天都变，PE 每天都变。
但库里存的是**前复权**价，除权后历史价格被整体缩放，用它反推历史 PE 会系统性偏低。
所以每日估值必须**按原值存**，不能"用收盘价现算"。

**存储分两张表，读取按一行：**

| 对象 | 粒度 | 用途 |
|---|---|---|
| `valuation` | 每只股票 1 行（最新） | 筛选、展示 |
| `valuation_daily` | 每只股票每天 1 行 | 历史序列、算分位 |
| `v_daily`（视图） | **日K + 当日 PE/PB/股息 合成一行** | 日常查询、K 线接口 |

```sql
-- v_daily 就是"一天一行"的完整快照
SELECT date, close, pe_ttm, pb, dv_ttm FROM v_daily WHERE symbol='600000' ORDER BY date DESC LIMIT 3;
-- 2026-11-13  10.40  6.69  0.46  4.04
-- 2026-11-12  10.21  6.57  0.45  (无)
-- 2026-11-11  10.17  6.54  0.45  (无)
```

不把列直接加进 `bars` 的原因：日线表 710 万行，加 4 个 REAL 列会让库从 679MB 涨到 900MB，
而目前只有 **0.08%** 的行有估值。按 (symbol,date) 键拆表 + 视图，读取体验相同、存储省 4 倍。

`valuation` 字段：

| 字段 | 含义 | 来源 |
|---|---|---|
| `pe_ttm` / `pe_static` | 市盈率（TTM / 静态） | 东财 `RPT_VALUEANALYSIS_DET` |
| `pb` | 市净率（MRQ） | 同上 |
| `ps_ttm` / `pcf_ttm` | 市销率 / 市现率 | 同上 |
| `industry` | 行业（如「银行Ⅱ」「白酒Ⅱ」） | 同上 |
| `dv_ttm` | **股息率 %** | 近 12 个月每 10 股派息合计 ÷ 10 ÷ 现价 |

`valuation_daily` 已回补 **1200 个交易日（5 年）**：2021-12-01 起，**622 万行**，库 1010 MB。
PE / PB / 股息率三项都有历史序列，因此都能算**分位**：

| 筛选 | 参数 | 含义 |
|---|---|---|
| PE 分位 ≤ | `max_pe_pct` | 当前 PE 低于近 **5 年** X% 的时间 |
| PB 分位 ≤ | `max_pb_pct` | 同上，看净资产口径 |
| 股息分位 ≥ | `min_dv_pct` | 当前股息率高于近 5 年 X% 的时间（越高越便宜） |

五年窗口和一年窗口的结论差别很大，这也是值得回补的原因：

| 股票 | PE 分位（1 年） | PE 分位（5 年） |
|---|---|---|
| 中衡设计 | 3.6% | **61.3%** |
| 浦发银行 | 66.0% | **75.6%** |
| 工商银行 | 98.8% | 99.8% |

中衡设计一年看是"极便宜"，放到五年里只是中位偏上 —— 单看一年窗口容易误判。

**股息率历史怎么算的**：股息率的分母必须是**不复权**收盘价（前复权价被除权缩放过，
会把历史股息率算高）。所以回补时单独取了一份新浪不复权价，按「过去 12 个月每股派息 ÷ 当日真实收盘价」
逐日计算，共写入 **369 万行**（3,754 只有分红记录的股票 × 1200 天），耗时 3.9 分钟。
受不复权数据源长度限制（1023 根），股息率历史从 2022-08 起，更早的日期为空。

序列形态是对的：随股价平滑变化，在除权日台阶式跳变 —— 浦发 2026-07-15 是 4.40%，
7-16 除权当天跳到 4.75%。

一次同步覆盖全市场：估值 12 页 + 分红 10 页，**6.8 秒**。5,579 只全部有 PE/PB，
其中 3,733 只有分红记录（其余不分红，股息率留空而不是填 0）。

**分位是预计算表 `valuation_pct`**：6.2M 行做窗口排名要 20 秒，不适合每次查询现算。
启动时后台算一次（约 27 秒）落表，查询直接读 5603 行，**0.8 秒**返回。

实测样例：工行 PE 8.21 / PB 0.79 / 股息 5.21%；茅台 PE 21.84 / PB 6.62 / 股息 3.62%；
安徽建工 PE 4.89 / PB 0.57 / 股息 6.8%。

上市日期与市值需要先补齐（各约 1 分钟 / 20 秒，只补空缺/刷新快照）：

```bash
python tools/build.py backfill     # 上市日期（东财 F10）
python tools/build.py mktcap       # 总市值快照（腾讯批量，5578 只 17 秒）
```

## 5. 数据库优化

> 为什么用 SQLite 而不是 PostgreSQL：见 [BENCHMARK.md](BENCHMARK.md)（同数据实测，
> 点查快 3 倍、简单聚合快 2 倍、存储省 1.8 倍；只在复杂窗口分析和多用户并发上落后）。

1.1 GB 的库、700 万根日线、620 万条估值，索引不是可有可无的：

| 索引 / 设置 | 作用 | 收益 |
|---|---|---|
| `bars(symbol,date)` 主键（聚簇） | 单只 K 线、逐票计算 | 0.2ms |
| `idx_bars_date` | 取某日全市场收盘价 | 34ms（原 3s 级全扫） |
| `idx_val_daily_date` | 取某日全市场估值 | **549ms → 34ms** |
| `idx_fav_notes(user_id,symbol,id)` | 笔记时间线 | 0.1ms |
| `idx_sessions_expires` | 会话过期清理 | 小 |
| `ANALYZE` | 生成 `sqlite_stat1` 统计信息 | 让规划器别猜 |
| `mmap_size=256MB` / `cache_size=64MB` | 读大表走内存映射 | 减少系统调用 |
| `PRAGMA optimize` | 每次同步/建库后自动刷新统计 | 长期不退化 |

代价要说清楚：`idx_val_daily_date` 占 **131 MB**（库从 1010 MB 涨到 1148 MB），
换来按日期查估值快 16 倍。这是有意的取舍 —— 时间序列表按日期检索是常态。

**哪些没加**：`valuation_daily(date, symbol)` 覆盖索引会让 131MB 变成 210MB，收益有限；
`favorites(user_id)` 不需要，因为主键 `(user_id, symbol)` 的前缀已经覆盖。

端到端实测（服务端）：

| 接口 | 冷启动首次 | 缓存命中 |
|---|---|---|
| 筛选（含分位） | 2.0 s | 4 ms |
| K 线 160 根 | 7 ms | — |
| 数据状态 | 646 ms | — |
| 登录态 | 16 ms | — |

筛选的 2 秒主要花在 pandas 聚合（8.7 万行户数 + 8.9 万行财务），不在 SQL 上；
同样条件重复查询走 120 秒结果缓存，4ms 返回。
## 6. Web 界面

```bash
python web/app.py --port 5001     # 或双击 web/启动.bat
```

启动后自动打开浏览器；**端口被占用会自动顺延**（5001 → 5002 …），并打印实际地址。

- **条件行**（参照富途牛牛的选股器）：每行左边是**中文指标下拉**（按 估值 / 财务 / 筹码 /
  行情 / 其他 分组），右边填「下限 ~ 上限」，点 `−` 删除；底部「＋ 添加条件」新增一行。
  条件之间是 **AND**。
- **同一指标可以加多次**，只要报告期 / 区间不同就是不同条件。例如：
  - 「净利同比(单季) 三季报 ≥ 30%」且「净利同比(单季) 年报 ≥ 30%」——两个口径都要达标
  - 「户数变化 近 1 季 ≥ 3%」且「户数变化 近 2 季 ≥ 8%」——短中期都在集中
  - 「户数变化 近 1 季 ≥ 0%」且「户数变化 近 3 季 ≥ 10%」——近期没再分散，长期在集中
- **报告期可选**：财务类指标多一个报告期下拉 —— **最新一期 / 一季报 / 半年报 / 三季报 / 年报**。
  选了具体期数后，**再出一个年份下拉**（默认「最新」，可选 2026 ~ 2016），
  精确到「2025 年一季报」这种粒度。
  表格对应列会显示该报告期的数值，结果栏会标注「营收同比=2025年年报口径」，
  避免筛选用年报、显示用最新的错位。同一指标挂多个报告期时，展示列取第一条，结果栏会列出全部口径。
- **跨年组合**：因为年份可选，能做「连续 N 年」的筛选，例如
  「2025 年报营收同比 ≥ 20%」且「2024 年报营收同比 ≥ 20%」且「2025 年报 ROE ≥ 15%」→ 126 只；
  也能对比同一期不同年份（2026 一季报 vs 2025 一季报）。
- **户数变化同样支持年份**：`户数变化 [近 1 季] [2025 年]` 表示「2025 年最后一个季末 vs 前一季」的变动，
  年份可选 2019 ~ 2026，默认「最新」。实测 2025 年近 1 季减少 ≥10% 命中 769 只，
  2024 年近 2 季减少 ≥20% 命中 268 只。
- **保存查询**：点「保存查询」给当前条件起个名字（如「红利股」），存进本地库；
  条件区下方会出现标签，点一下即可载入整套条件并立刻筛选，标签上的 `×` 删除。
  同一名字再保存一次是**覆盖更新**，不会重复堆叠。
- **内置四个方案**（首次启动自动写入，之后删掉不会再冒出来）：

  | 方案 | 条件 | 命中 |
  |---|---|---|
  | 筹码集中 | 户数近 1 季降幅 ≥5%、近 3 季 ≥15%、近三季净利 ≥0.1 亿、排除 ST | 188 只 |
  | 红利 | 股息率 ≥4%、PB 分位 ≤40%、ROE ≥8%、排除 ST | 148 只 |
  | 高股息 | 股息率 ≥6%、股息分位 ≥70%、排除 ST | 77 只 |
  | 高成长 | 营收同比 ≥30%、单季净利同比 ≥30%、ROE ≥12%、排除 ST | 208 只 |

  这些只是**起点**，载入后可以随意改条件再另存为新方案。
- **搜索框（代码 / 名称 / 拼音）**：输入即出下拉补全，支持四种匹配
  **代码**（`600874` 或 `60`）、**中文名**（`创业`）、**全拼**（`chuangye`）、
  **拼音首字母**（`cyhb`）。`↑` `↓` 选择、`Enter` 确认并直接打开该股 K 线、
  `Esc` 收起下拉（再按一次清空）。框右侧 `✕` 一键清空并恢复筛选；
  关键字同样会作用到筛选接口（`?keyword=cyhb` → 只留创业环保）。
  拼音索引由 build_pinyin.py 生成（约 100 行，无需第三方库，Unihan 读音表，

### 形态选股（做小做底 / 旗形）

**按需计算 + 当天缓存**：不再预先跑完 54 个组合。查询里用到哪个组合才算哪个，
结果写进 `pattern_signal` 表并记 `meta` 标记（`pat:<交易日>:<组合列>`）：

| 场景 | 耗时 |
|---|---|
| 启动预热（后台读日线进内存） | ~30 秒，不阻塞请求 |
| 某组合当天第一次查询 | **1.4 秒** |
| 同一天同一组合再查 | **0.02 秒**（缓存） |
| 换一个组合（日线已在内存） | 1.4 秒 |
| 做小做底 | 1.2 秒 |

缓存按**交易日失效**：新 K 线进来（`bars` 最大日期变化）后标记对不上，会自动重算。
面板「形态信号」显示 `已算 N/58 组合`，点「同步」= 清掉当天缓存强制重算。

build_patterns.py 仍保留，用于手动预热全部组合（约 **24 秒**），结果落 `pattern_signal` 表，
宽表查询时只做一次 join，界面上不增加等待。日线更新后在「本地库」里点
**形态信号 → 同步**即可刷新（也注册进了 `sync.py` 的 `patterns`）。

**做小做底**（定位：股票池过滤器，不要单独当买入信号）

| 现价距**历史最低** `现价/最低−1` | ≤ 45% | 真正的"低位"，而不是区间分位 |
| 近 2 年振幅 `(最高−最低)/最低` | ≤ 45% | 长时间窄幅横盘，才是筑底 |
| 近 2 年任意 20 日涨幅上限 | ≤ 28% | 中间没有大行情 |
| 2 年最低点距今 | ≥ 60 个交易日 | 底部守住，不是还在创新低 |
| 现价高于 2 年最低 | ≥ 3% | 排除破位 |
| 20 日均成交额 | ≥ 2000 万 | 小盘筑底股普遍不活跃，门槛不能太高 |
| 上市满 2 年、排除 ST | — | — |

**低位放量**（低位 + 连续多日放量 + 量价配合 + 可交易性过滤）

主条件全部满足才命中：

| 维度 | 条件 |
|---|---|
| 低位 | 收盘在 250 日区间的位置 ≤ 30%（可调 30/40/50%）；且距 250 日最高收盘回撤 ≥ 25% |
| 连续放量 | 最近 5 个交易日里存在「连续 K 日」满足 `量 > 前20日均量 × 基准`；K = 3/4/5 |
| 放量强度 | 温和 `1.2×/1.5×`、标准 `1.5×/1.8×`、强势 `1.8×/2.5×`（前值=连续放量门槛，后值=其中至少 2 天要达到） |
| 量能抬升 | `vol_ma5 > vol_ma20 × 1.2`，且 5 日均量比 5 天前抬升 |
| 量价配合 | 放量段收阳 ≥ 2 天；累计涨幅在 −3% ~ +15%（低位放量不该已经大涨） |
| 无效放量过滤 | 单日量 > 5×均量 不算；`high == low`（一字板/停牌）剔除 |
| 流动性 | 近 20 日日均成交额 ≥ 5000 万；放量段日均换手率 1% ~ 10% |
| 可交易 | 非 ST、上市 ≥ 120 日、当日不是涨停封死（`close < 涨停价 × 0.995`） |

2026-11-17 实测（已排除 ST）：

| 3 日 · 分位≤40% | 47 | 34 | 18 |
| 4 日 · 分位≤30% | 38 | 20 | 10 |
| 5 日 · 分位≤30% | 22 | 9 | 1 |

- 神州数码 000034：位置 0.18，量比 1.74，换手 4.46%，放量段涨 6.57%，当天仍在放量
- 宁波华翔 002048：位置 0.14，量比 1.36，换手 9.81%，放量段涨 −0.79%，结束后第 3 天

> 量能对比用的是**前 20 日均量**（`_prev_mean`，不含当日），避免当天放量把基准拉高。

**行业筛选**：条件下拉里选「行业」，两个下拉分别是**属于 / 不属于**和 128 个行业
（按成分股数量降序，括号里是股票数）。加多条行业条件时彼此是**「或」**关系——
例如「半导体 + 医疗器械」= 两个行业都算，而不是取交集；中途可以掺「不属于 银行」做排除。
接口是 `GET /api/industries`，数据来自东财行业分类（`valuation.industry`）。

**净利润的变化**分三种口径，这是最容易踩坑的地方：

- **净利同比(累计)** = 东财的 `SJLTZ`，年初至今累计的同比
- **净利同比(单季)** = 单季净利 ÷ 去年同季 − 1
- **净利环比(单季)** = 单季净利 ÷ 上一季 − 1

单季和累计会打架。实测：万源通三季报单季同比 **+73.4%**，但累计同比 **−3.6%** ——
说明最近一个季度在改善，前面几个季度太差。只看累计会漏掉这种拐点股。

不同报告期口径结果差别也很大，同一条件（营收同比 ≥ 30%）：**最新一期 822 只 / 年报 634 只 /
一季报 938 只**。

实现上先算一张 **5578 行 × 391 列** 的宽表（`metrics.py`），再对条件做向量化过滤。
这比之前逐条 SQL 拼接快得多，也顺带解决了筛选 2 秒的问题：现在冷启动 0.9~1.5 秒、
重复 0.02 秒。

> **宽表构建方式**：所有派生列先攒进 dict / list，最后一次性 `pd.concat` 合并。
> 早期版本是几百次 `df[col] = ...`，pandas 会不断插入新 block，
> 产生一堆 `PerformanceWarning: DataFrame is highly fragmented` 并且首次加载要 4 秒。
> 另外 `metrics()` 加了 `threading.Lock`，多个标签页同时打开时只建一次表。

### 成交量单位事故（2026-11 修复）

**现象**：603679 在 2026-10-08 的成交量显示 577.4 万，真实值 5.77 万，差 100 倍；
而且不止这一只——全市场平均成交量在 10-08 突然从 89 万跳到 557 万。

**根因**：各数据源的成交量单位不一致，而且**按板块还不一样**（2026-11 后续排查补充）：

| 源 | 主板 / 创业板 / 北交所 | **科创板 688/689** | 复权 |
|---|---|---|---|
| 东财 `push2his` | 手 | 手 | 前复权 |
| 腾讯 `proxy.newfqkline` | 手 | **股**（差 100 倍） | 前复权 |
| 新浪 `quotes.sina.cn` | **股** | **股** | **不复权** |

平时增量同步走腾讯，单位是手；一旦东财/腾讯被限流、降级到新浪，最近 40 天的成交量
就被按「股」写进库，于是出现 100 倍误差。新浪还是**不复权价**，混进前复权表连价格口径也会坏。
更隐蔽的是**腾讯对科创板也返回股**——618 只科创板股票的成交额全部放大 100 倍
（688001 会算出 550 亿/天），但主板的量看起来完全正常，从日志里根本发现不了。

**修复**：
1. `_sina_sym()` 把 `volume / 100` 统一换算成手（新浪所有板块都是股）
2. `_txp_bars()` / `_tx_bars()`：科创板（688/689）的 `volume / 100` 换算成手
3. `fetch_bars_recent()`（每日增量）**只允许前复权源**（txp / em / tx），
   拿不到就跳过这只、等下一轮再补，绝不把新浪的不复权数据写进库
4. `tools/repair_bars.py` 用腾讯重拉最近 90 天覆盖，修好 49.9 万行（3.6 分钟）
5. `tools/repair_kcb.py` 重建 618 只科创板全历史（71.3 万行，1.1 分钟）
6. `repair_symbols.py <名单>` 重建「老数据不复权 + 股单位」的遗留股票（这次 30 只）
7. `build.py validate` 新增**成交量量级体检**：相邻交易日全市场中位倍数超过 5 倍就告警

```
python tools/build.py validate                  # 体检，含成交量单位检查
python tools/repair_bars.py 90                  # 最近 90 天重拉覆盖
python tools/repair_kcb.py                      # 科创板全历史重建
python tools/repair_symbols.py 名单.txt          # 按名单重建
```

修复后 603679：09-30 = 6.14 万手、10-08 = **5.77 万手**，与行情软件一致；
各板块日均成交额中位数回到 **0.43 ~ 1.57 亿**（修复前科创板中位 123 亿）；
全市场各日中位倍数在 0.8~1.2 之间，无跳变。

### 股息率缺失的修复（2026-11）

**现象**：某天之后大量股票的股息率变成空，`股息率 ≥2%` 这类条件把票全筛掉了。

**根因**：`sync_valuation` 用「当天日线的收盘价」算股息率，当天停牌或还没出数据的股票取不到收盘价，`dv` 就被写成 `NULL`；再加上分红窗口只有 365 天，年付息股在「除权刚满一年、下一次还没派」的空档也会变空。

**修复**：
1. 收盘价改成「每只股票最近一根日线」的价格（回看 15 天），停牌股也能算
2. 分红取 3 年：近 400 天有记录按 TTM 累加，没有就回退到**最近一次分红**
3. 分红记录抓取少于 500 条时（上游没抓全），**保留库里原有股息率**，不整列冲空

修复后有股息率的股票从 2254 只恢复到 **4471 只**。

### 用户与收藏

- 右上角「登录 / 注册」：用户名 2~20 字符、密码 ≥6 位；注册后自动登录
- 密码用 **PBKDF2-HMAC-SHA256（20 万次迭代 + 随机盐）** 存库，会话是随机 token，
  走 `HttpOnly; SameSite=Lax` Cookie，有效期 30 天
- 登录后结果表最左侧出现 ★，点一下加入收藏；顶栏出现「★ 收藏 N」
- **分组**：收藏面板顶部是分组 chips（全部 / 未分组 / 自定义），`+ 分组` 新建、
  双击重命名、`×` 删除（组内股票回到未分组）；每只票右侧下拉可直接改分组；
  在某个分组下点 ★ 收藏，会自动归入该组
- **笔记时间线**：每次「记录」都是**追加**一条，不覆盖；每只票展示最近一条 + 「历史 N 条」，
  展开后是带时间戳的完整记录（可单条删除）。这样复盘时能看到"什么时候跟进的、当时怎么想的"
- 每个用户的数据完全隔离；未登录调用收藏接口返回 401

| 接口 | 作用 |
|---|---|
| `POST /api/register` `POST /api/login` `POST /api/logout` | 账号 |
| `GET /api/me` | 当前用户 + 收藏 + 分组 |
| `POST /api/fav` | 收藏（可带 `group_id`） |
| `POST /api/fav/delete` | 取消收藏 |
| `POST /api/note` | 追加一条笔记 |
| `GET /api/notes?symbol=` | 该股的时间线 |
| `POST /api/note/delete` | 删除一条笔记 |
| `POST /api/group` | `action=create/rename/delete/assign` |

ROE 取**最新报告期加权 ROE 年化**，因为 A 股 ROE 是年内累计数，Q1 的 3% 和年报的 12% 不能直接比。

自检脚本：`python web/check_ui.py [url]`（校验 HTML/JS 元素对应关系与四个接口）。

**技术说明**：Flask 在当前环境装不上（PyPI 下载被拦，清华镜像同样超时），所以用标准库
`http.server` 实现，零依赖。路由是 Flask 风格的五条：

| 路由 | 作用 |
|---|---|
| `GET /` | 首页 |
| `GET /api/screen?...` | 选股，返回 JSON（带 120 秒缓存） |
| `GET /api/kline/<code>?n=160` | 个股日线 |
| `GET /api/datasets` | 各数据集状态与上次同步时间 |
| `POST /api/sync?kind=bars` | 触发同步（后台线程），`GET /api/sync/status?id=` 查进度 |

同步在后台线程执行，期间界面照常可查（SQLite WAL 读写不互斥）；任务完成后自动清空查询缓存并重跑一次筛选。
